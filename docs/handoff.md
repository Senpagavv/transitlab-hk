## 4. 四项已拍板的建模决定（**不要推翻**）

发起人 2026-09-16 明确选择：

1. **基准年 = 2026 现状年**。用规划署《2023–2031 人口分布推算》把 2021 普查人口推到 2026。
   建筑（2026-08）、学额（2025/26）、跨境（最近 12 周）本来就是当期数据。
   好处是能和实时车流直接对比。
2. **完整均衡分配**。容量约束均衡，输出逐路段流量，目标 **GEH < 5**（英国 TAG/DMRB 标准，
   要求 85% 的路段达标）。这是"能拿出去讲"的硬指标。
3. **方式全要**：私家车/的士、港铁+轻铁、巴士+小巴、步行+单车。绿色交通赛道，步行和单车是加分项。
4. **小区全港细分到约 450 个**，对齐官方 CTS 的 454 个。已完成，现为 455 个（9/17 晚合并无人碎片后）。

2026-09-17 追加三项：

5. **沙盘两档速度**：拖动时几秒内给**即时估算**；点「完整计算」等一两分钟得到正式的均衡分配结果。
   即时估算必须在界面上标明是近似值。
6. **演示片区暂不定**：等全港基线结果出来，看哪里的问题最有故事性再选。沙盘四个杠杆按原顺序做
   （加人口/改用地 → 画新线路 → 改隧道收费 → 加单车径）。
7. **9/17 当天顺序**：模型为主（2026 人口 → 步行网络 → 小汽车/公交时间矩阵），收尾把 464 个小区放上网站，
   让发起人能亲眼检查数据。

2026-09-17 晚追加：

8. **步行/单车 = 机动化对账 + 步行单车估算**。出行调查只公布机动化出行总量（步行、单车因漏报严重没有公布总量，
   只有目的比例和时长分布：步行平均 12 分钟、64% 在 10 分钟内；单车平均 24 分钟）。所以第一步只生成机动化出行并逐项对账；
   步行、单车在第三步作为短途备选方式加入，按报告的时长分布调参，网站上标"估算"。

其他早期决定：全港覆盖（不是单走廊）；**数据全部离线预制**，AI 只检索预制数据，不现场抓 API 建图；
同一引擎两种界面（教学版 / 专业版）。

## 6. 踩过的坑（**最值钱的一节，逐条都是真实事故**）

每一条都是"程序不会报错，但结果是错的"那一类。**接手后如果觉得某条设定别扭想改回去，先读这里。**

### 6.1 Esri 的「按工作地点划分」图层其实是按居住地

ArcGIS 上有个图层叫 *Hong Kong Working Population Distribution **by Place of Work** by Small TPU in 2021*，
字段是 `plw_same / plw_diff_hk / plw_diff_kln / ...`，看起来正是吸引端的就业数据。

**它不是。** 逐值比对 166 个重叠小区，与我们已有的居住地版本 **100% 相同**。标题具有误导性。

👉 **结论：香港没有公开小区级就业岗位数。** 不要再找了。改走楼面面积路线。

### 6.2 `TRAVEL_DIRECTION` 的含义和字面直觉相反 ⚠️ 最严重

运输署路网：**`1` = 双向，`3` = 沿数字化方向单行**。

按直觉理解（1=单行）会让强连通分量只剩 **58.9%**、464 个小区只有 337 个接入主网。
**模型照跑、不报任何错、结果全错。**

三重证据定案：
1. 连通性 58.9% vs **97.7%**
2. 毕打街、云咸街、通菜街三条确定的单行道**全部编码 3，无一条 1**
3. 用 807 个实时探测器的罗盘行车方向比对几何走向，无歧义样本 **90% 一致、0% 相反**

### 6.3 限速图层不含 50 km/h

`SPEED_LIMIT` 图层只覆盖 9.3% 的中心线，取值只有 30/70/80/100/110。
**因为 50 km/h 是香港法定默认限速，图层只记录"例外"。** 没挂上的是 50，不是"未知"。

### 6.4 GTFS 里港铁站叫「Platform 1」

港铁每个站台是独立 stop，全部叫 `Platform 1`~`Platform 8`，**真站名在 `parent_station`**（97 个）。
按 `stop_name` 归并会把 98 个站压成 7 个。轻铁站点则有真名、无 parent。

👉 正确写法：`parent_station.fillna(stop_name)`，得 161 站。
这个错误当时表现为审计里"只有 18% 小区靠近铁路"这个反常数字。

### 6.5 公营房屋不在屋宇署登记里

屋宇署只登记**私人**楼宇。如果按 `use == 'residential'` 分摊人口，**每个公屋邨都会被分到零人口**。

验证过三种定义：

| 定义 | 每户楼面 |
|---|---|
| 仅私人住宅 | 45 m²（太低，漏公屋）|
| 私人住宅 + 全部未分类 | 95 m²（太高，混入政府/学校）|
| **私人住宅 + 未登记塔楼(层≥3 且占地<2000m²)** | **77 m²** ✅（合理带 70–90）|

### 6.6 裙楼不是商场

住宅塔楼下的裙楼共 **33.3 百万 m²**，是全港私人商业存量（11.8 百万）的近 3 倍。
它们主要是**停车场和会所**，不是商场。真正的商场（Elements、德福广场）本来就登记在 Office/Commercial 里。

把裙楼一刀切成零售，会让零售楼面变成官方的 4.49 倍。现归为 `residential_ancillary`，**不套用商店的吸引率**。

### 6.7 酒店被归在商业里，但 RVD 商业存量不含酒店

屋宇署把酒店登记为 Office/Commercial，导致尖沙咀 2.13 倍、中西区 1.90 倍、湾仔 1.89 倍。
按名称识别拆出来后，**每间客房 63.3 m²**，与官方 93,456 间完全吻合。

同理，逐区比值偏高的地方都有名有姓、都不是错误：
**大埔 7.73 = 科学园、西贡 7.55 = 将军澳工业邨、离岛 = 机场、南区 = 数码港**——都是政府持有，不计入 RVD 私人存量。
工业 1.64 倍偏高也是这个原因。

### 6.8 香港的「College」是中学，「博愛醫院」是办学团体

按名称识别大学和医院时：
- 何福堂**書院**、董玉娣中學（English 名是 `... College`）、警察學院、海關學院 → 全是误报
- **博愛醫院**鄧佩瓊紀念中學 → 是学校不是医院

不加过滤的后果：每名学生 226 m²（应为 8–40）、每床 512 m²（应为 60–200）。
现在的规则：大学只认 `universit|polytechnic|大學`；医院认 `hospital|醫院` 但排除 `college|school|中學|substation|quarters|宿舍`。

### 6.9 统计表里的小计行

教育局分区学生表有 `All Districts` 总计行 + 3 个大区小计 + 18 个区。全加一遍 = **3 倍**。
（小学一度算成 951,699，实际 317,233。）

👉 现在脚本里有断言：**18 区之和必须等于表中总计，否则抛异常。**

### 6.10 名称前缀吞并

`"Lok Ma Chau"` 是 `"Lok Ma Chau Spur Line"` 的前缀。用 `startswith` 匹配，落马洲会把支线的跨境学童也吞掉
（分配出 21,548 名，实际只有 16,656 名）。

👉 改成精确映射表 `EDB_POINT_NAMES`，并加断言：教育局以后改口岸名会直接报错，不会静默算错。

### 6.11 普查表里的 `-` 要分字段判断

计数字段（人口、公屋住户数）的 `-` 是**零**；比率和均值的 `-` 是**未公布**，必须留空。
一刀切当缺失会让 124 个小区"没有公营房屋"。改对后全港公屋占比 30.2%，官方 29–30%。

### 6.12 建筑层数字段本身有错

有记录写「41 层」但楼高只有 14.1 米。**2,789 条公布层数与建筑自身高度矛盾**（层高 <2m 或 >8m），
一律丢弃改用高度推算。

另外层高随占地规模变化（数据自身规律，不是假设）：
<100 m² → 3.31 m/层；3k–10k m² → 4.10；>10k m² → 4.50。
不分档会把机场客运大楼、会展、启德体育园这类大跨度建筑算成 13–20 层。

### 6.13 三维堆叠不会重复计算（这条是**证伪**，不是错误）

曾怀疑塔楼楼面会和裙楼重复计算。实测 Austin Station：裙楼顶 20.1m，其上塔楼 `BaseHeight` 正好 = 20.1；
Grand Austin 各塔从 19.0–19.6m 起算。**这是规范的三维堆叠模型，不存在重复。**

记录下来是因为：**结构性风险要主动设想并证伪，不能因为"看起来没问题"就跳过。**

### 6.14 其他

- ATC 普查表的行标签不在第 0 列（有的在第 17/30/39 列）→ 用位置无关的 `row_cells()`
- ATC 单方向站点的第二个方向块全是破折号，会覆盖已读到的值 → **永不用空值覆盖非空值**
- 地政总署搜索 API 对默认 `python-httpx` UA 返回 403 → 用自定义应用 UA
- CSDI `portal.csdi.gov.hk/csdi-webpage/download/common/...` 会 403「Service unavailable」，
  但 `static.csdi.gov.hk/csdi-webpage/download/<hash>/<format>` 可用
- 幼稚园总数曾用假设值 140,000，官方是 **115,300**（高了 21%）——**不要用假设值，去找官方表**
- 331 条屋苑环形支路是首尾相接的闭环，最短路永远走不到 → 标 `routable=False`

### 6.15 隧道是两个方向相反的隧道管，收费要两个方向各放一次

每条收费隧道在路网里是**两条方向相反的单行中心线**（方位角相差约 180°，高程字段都是 −1）。
只把收费放在"最长的一段"上，结果只有一个方向交钱——**港岛↔九龙有 9,813 个小区对免费过海**，
观塘→中环 0 元、屯门→中环 60 元但中环→屯门 0 元。

👉 现在按方向分组，每个方向最长的地下路段各收一次。小汽车矩阵的审计会检查
**港岛↔九龙 20,280 个小区对必须全部交隧道费**，这个检查就是抓出此错的那一个。

### 6.16 离岛没有公路，不能给它们接一条跨海的假路

旧的接驳逻辑是"小区里没有路口就挂到最近的路口"。长洲（小区 920）最近的路口在 **6.3 公里外的海对面**，
模型于是算出了"从长洲开车到中环"的时间。

👉 现在小区边界 300 米内都没有路口的，判定为**无公路连接**，小汽车不可达：
**南丫岛 911S、长洲 920、坪洲 976**，以及沙田一个 45 人的山坡碎片 757.9，共 31,479 人。
他们靠渡轮进出，由公交矩阵负责。审计要求到不了的小区对**全部**涉及这几个小区。

### 6.17 小区锚点会落在山上

大小区的几何中心可能在山坡上。沙田 756S.4 住了 3.3 万人，锚点却离最近路口 3 公里，
每趟行程凭空多出 7 分钟。

👉 接驳点改为围绕**楼面加权的活动中心**选（住宅和工作场所都产生出行，所以全部楼面都算），
再吸附到最近的真实建筑以保证落在小区内。接驳距离 90% 分位从 670 米降到 375 米。

### 6.18 普查小区会横跨两个区议会分区

普查小区按规划单位划分，与区议会边界并不对齐。用"代表点落在哪个区"整块归区，
**荃湾比规划署少 32%、葵青多 24%，观塘少 16%、西贡多 20%**——差额总是成对出现在相邻区之间，这就是线索。

👉 改为按**住宅楼面实际落在哪个区**分摊，横跨两区的小区按比例拆开。修正后 18 区全部在 1.05% 以内。

### 6.19 已知的小瑕疵（不影响模型，记录备查）

- 小区细分产生了两个极小的碎片：**757.9（45 人，沙田山坡）**、**156S.2（62 人，柏架山雷达站）**。
  出行量可以忽略，以后可考虑把 500 人以下的碎片并入相邻小区。
- 小汽车矩阵有 66 对绕行系数 >4 的小区对未被"跨海 / 翻越郊野"判据自动解释。
  抽查最严重的几对（马鞍山↔西贡、东涌↔梅窝、山顶↔薄扶林）都是翻山；
  判据漏掉它们，是因为这些大小区同时含屋苑和郊野，平均密度超过 100 人/km²。

### 6.20 deck.gl 的"插层模式"在 MapLibre 6 上什么都不画

为了让小区填色压在地名下面，把 deck.gl 切到 `interleaved: true`——结果**小区和实时车流全部消失**，
图例和数据都正常加载，控制台没有任何报错。

👉 小区改用 **MapLibre 原生图层**（`<Source>` + `<Layer beforeId=…>`），插在第一个地名层
（source = `landsd-label`，底图第 815 层起）之前；deck.gl 恢复叠加模式，只画车流。
另外 deck 的画布层级高于地图里的浮动面板，面板和图例的 `z-index` 必须 ≥ 3，否则车流线会画到卡片上。
检查脚本：`node frontend/scripts/check-zones.mjs map-check/zones`。

### 6.21 r5py 1.1.7 逐个起点串行计算，20 个核只用 1 个

`TravelTimeMatrix` 内部是一个普通的 Python 循环（源码 `travel_time_matrix.py` 第 98 行），
定义了线程数却没用上。全港公交矩阵串行要 **42 分钟**（5.4 秒/起点）。

👉 `pipeline/18` 现在把起点分块放进线程池（R5 计算时会释放 Python 锁），实测 **1.6 秒/起点**。
沙盘"完整计算"要反复算矩阵，这个速度很重要。

另外两点：
- **R5 必须跑在 Java 21 上**。直接运行时 JVM 查找器会找到机器上另一个 Java 8（`C:\Java\jre1.8.0_503`）然后失败。
  `pipeline/18` 在导入 r5py **之前**从 `.env` 读 `JAVA_HOME`。
- 香港 93% 的班次按发车间隔编排，R5 随机抽取发车时刻取中位数，**同一对小区两次计算会差 1–2 分钟**。这是方法本身的抽样误差，不是错误。

### 6.22 小区命名：楼座名没人认得

小区编号（"756S.4"）对读者没有意义。最初用"区内最大命名建筑"，结果满屏"翠树楼""明星楼"——
公屋楼座的中文名不带屋邨名。长洲、南丫岛没有巴士站，一度叫"豪泽阁""南丫发电厂大楼"。

👉 `pipeline/19` 的命名顺序：铁路站 → 屋邨/屋苑（从巴士站名截到"邨/苑/新村"）→ 岛名（地政总署官方地名库，
限小区最大那块陆地）→ 非道路的巴士站地名 → 官方地名（村、山）→ 楼座名 → 区名。
"花园""城"不能当屋苑标志（"观塘海滨花园"是公园，"九龙城"是区）。

### 6.23 Bash heredoc 把 `\n` 变成了真的换行

通过 heredoc 往 TSX 里写 `` `…\n…` ``，结果写进去的是一个真换行。JS 模板字符串允许换行，所以**编译通过、功能也对**，
但下一次按原文匹配替换时就找不到了。

👉 大段代码一律用写文件工具，或者先写成 `.py` 补丁脚本再运行；已写入的内容按位置切片替换，不要逐字匹配。

### 6.24 算了一小时，保存之前崩了

全港公交矩阵串行算了约一小时，三张矩阵都算完，然后在**保存之前**的一行审计代码上崩溃（给 R5 传了一张表，它要的是一个点），结果全丢。
试跑（`--sample`）之所以没发现，是因为它在那一行之前就提前返回了。

👉 两条规矩：**昂贵的计算结果第一时间落盘，审计放在保存之后**；**试跑必须走完整条代码路径**（包括保存和审计，写到单独的 `.sample` 文件）。

### 6.25 社区版 GTFS 的渡轮只有一个方向——而合并官方版本来就在计划里

只用社区版 GTFS 算公交矩阵，结果**坪洲从 433 个小区都进不去、长洲到中环要 151 分钟**。原因：
社区版（由 OpenStreetMap 推导）里中环–坪洲只有坪洲→中环的班次，中环–长洲早上没有从长洲开出的船，
230R（往马湾）有一个方向被归到"只在周末行驶"。

`docs/reuse-and-references.md` 在 9/15 就写好了计划：**港铁、轻铁用社区版，其余用运输署官方版**。
我跳过了合并，这才是根因。

👉 `pipeline/17b_transit_feed.py` 做合并，官方版 2,452 条线全用，社区版只取港铁 10 线 + 轻铁 11 线，
两边 id 分别加 `td:` / `osm:` 前缀；审计检查引用完整、id 唯一，并**逐条检查渡轮早高峰是否两头都开船**。

### 6.26 官方 GTFS 的网址格式 R5 不认

联营线路（九巴+城巴）的 `agency_url` 写成 `https://a|https://b`，部分线路网址里有空格。R5 拒绝读取整份文件。
👉 合并时只保留第一个网址、空格转义为 `%20`，并加审计检查。

### 6.27 r5py 按文件名缓存输入，改过的文件会被悄悄忽略 ⚠️

r5py 把输入文件复制到自己的缓存目录（`%LOCALAPPDATA%\r5py\`），**只要同名文件已存在就不再复制**。
合并表第一次有错被缓存下来，修好后 R5 读的仍是旧文件，报同样的错。
**沙盘改线路后重新生成班次表时，这会让模型悄悄用旧数据。**

👉 `pipeline/18` 的 `staged()`：输入文件按内容指纹重命名后再交给 r5py（`data/cache/r5-inputs/`），内容一变名字就变。

### 6.28 r5py 把"起点编号 = 终点编号"的格子一律写成 0 分钟

源码 `travel_time_matrix.py` 第 158–161 行。只要编号相同就是 0，不管两点是否同一位置。
我检测"小区中心能否走到最近车站"时两边用了同一个小区编号，结果华明邨被判为 0 分钟可达，检测形同虚设。

👉 车站点的编号加 `|stop` 后缀。以后凡是"同一小区的两个不同点"都要用不同编号。

### 6.29 步行孤岛：活动中心落在与街道不相连的碎片上

**粉岭华明邨（628.1，2 万人）**的活动中心吸附到一段 OpenStreetMap 里没接上公共街道的步行道，
进出全部不通——而 57 米外的巴士站到粉岭站只要 17 分钟。**南丫岛（911S）**的活动中心被发电厂的巨大楼面拉进厂区，
厂区道路与村路不相连。

👉 `pipeline/18` 先测每个小区"中心 ↔ 最近车站"双向步行，任一方向不通就改用该车站作起终点，并在审计中列出。

### 6.30 官方巴士中途站时间是按直线距离插值的，高速段被高估

官方 GTFS 每个巴士班次只写首末站时间（88% 空白），R5 按站间直线距离分配。高速公路段距离长、车速快，
却分到大半时间：960 线屯门市中心→中环车上 **53 分钟**，社区版逐站时间是 **35 分钟**。

👉 `pipeline/17b` 的 `fill_bus_stop_times()`：按**路网自由流车程 + 每站 0.4 分钟停站**分配，再缩放到官方首末站时间。
修正后该段 **38 分钟**。电车、渡轮仍由 R5 插值（站距均匀／中途停靠少）。
注意：scipy 建稀疏图会把平行路段的车程**相加**，必须先按节点对取最小值。

### 6.31 人口推算已被实际数据超越——对齐统计处

回测规划署 2023 年的推算：2023 −0.5%、2024 +0.04%、2025 +0.8%、**2026 +1.0%**。统计处已公布 2026 年中估计（临时数，7,518,300）。
👉 `pipeline/16` 的 `calibrate()`：各年龄段总数对齐统计处（web table 110-01002），规划署只决定人住在哪里。
**统计处的 2026 数字是临时数，正式数公布后重跑 16 → 19。**

### 6.32 后台任务不要用 `&` 串起来

`A && B && C &` 会把整条链丢到后台，不受管控、跑完没有通知，日志文件还会被锁住读不了。
👉 长任务一律用工具的"后台运行"方式单独启动。

### 6.33 R5 只让乘客下车后步行约 2 公里——偏远小区"出得去、进不来"

梅子林（沙田山村）公交矩阵"出 99%、进 11%"。先怀疑 OpenStreetMap 里的 `access=private` 步道，**查实不是**：
中心与最近车站之间双向都能走通。真正原因是 R5 为"车站→目的地"预先建步行距离表时有约 **2 公里**上限，
而"出发"是完整的街道搜索，不受这个限制。

👉 `pipeline/18` 的 `access_points()`：中心与最近车站（3 公里内）之间**任一方向不通，或单程步行超过 30 分钟**，
都改用该车站作起终点，并把那段步行时间**加回所有进出该小区的行程**（能走通的方向取实测；都走不通按直线 × 1.3 ÷ 步速）。
梅子林修正后"出 100%、进 100%"。共识别 8 个小区：柏架山 34 分钟、曾咀 24、天恒邨一带 32、华明邨 1、
观音山村 39、梅子林 41、西贡白沙湾 35、南丫岛 34（分钟为补回的步行时间）。

教训：**说出"原因"之前要先用数据排除其他可能**。私人通道的说法我一度告诉了发起人，后来才证伪。

### 6.34 小区中心被工业楼面拉走——曾咀的居民被放到了只有早上 9 点后才有车的站

曾咀 431S 的公交出发中位时间 185 分钟。时刻表没错：曾咀站只有 K52 支线，平日 08:00–17:00 每小时一班，
从曾咀开出的首班 09:00。错在**小区中心**：按"所有楼面面积同等加权"，54 万 m² 的环保园、内河码头
把中心拉到了工业区，离 2,300 名居民所在的龙鼓滩村 2.4 公里（村口的 K52 主线 9–20 分钟一班）。

👉 `pipeline/15` 的 `activity_centres()` 改为**出行端点加权中位点**：每栋楼按 `pipeline/21` 算出的出行端点加权
（住宅楼承担居民的出行，写字楼/商场/工厂承担各自的吸引），取到其他所有楼加权距离最小的那栋。
中位点一定落在较重的那一簇，不会落在两簇之间的荒地上。
⚠️ 因此 **`pipeline/21` 必须在 `pipeline/15` 之前跑**（编号顺序不代表运行顺序，见第 9 节）。

### 6.35 住宅判定有两个方向的错：漏了村屋，多了学校

旧规则"未登记 + 塔楼 + ≥3 层 + 占地 < 2000 m²"：
- **漏**：村屋高约 7.8 米、占地约 64 m²，被估成 2 层 → 不算住宅。3.3 万栋，集中在元朗、大埔、西贡、北区。
- **多**：1,112 栋≥3 层的未登记设施被当成住宅，其中 **404 所学校**、104 个车站，共 625 万 m²。

还有一个根源：`pipeline/09` 用单一层高换算层数，**8–9 米的小楼 90% 实为 3 层**（公布层数的楼宇里 4,030 对 430），
却被估成 2 层（35,907 栋）。

👉 `pipeline/09`：15 米以下按"同占地档、同一米高度的公布层数中位数"查表（样本 ≥50 才用）。
👉 `pipeline/10`：新增 **`dwelling` 列**，是全项目**唯一**的住宅定义（村屋：40–150 m² 且 ≥2 层；
名称含学校、车站、变电站等则排除，含"House/Court/邨/苑"等住宅字样的除外）。`pipeline/14/16/21` 都只读这一列。
教训：**同一个定义复制到三个脚本里，改的时候必然漏改**——规则只能有一处。

### 6.36 `pipeline/14` 拿普查小区编号去匹配"模型小区"那一列——一重跑就不再细分

`buildings-classified.parquet` 的 `zone` 列由 `pipeline/10` 填写，而 10 读的是**模型小区**（细分之后的）。
14 却用它去匹配**普查小区**编号：被细分过的普查小区一栋楼都匹配不上，重跑时会**悄悄地不再细分**，不报错。
这个错一直没触发，只是因为 14 之后没再重跑过。

👉 14 现在自己按坐标把楼宇归到普查小区（`dwelling_buildings(census)`）。

### 6.37 细分出的"无人碎片"

旧细分留下 36–111 人的小区（马鞍山、大潭的山坡），其中一个连公路都没有。但不能简单按人口合并：
**葵涌货柜码头只有 66 名居民**，国泰城 113 人，它们是重要的就业区。

👉 `pipeline/14`：某一份**人口 < 500 且非住宅楼面 < 5 万 m²** 时，少切一份重新聚类。结果 464 → **455 个小区**，
无公路小区只剩真正的离岛（南丫岛、长洲、坪洲）。

### 6.38 出行调查只数"机动化出行"，而且调查时边境还没开

- 步行、单车没有公布总量（报告明言漏报严重、无法校正）。长洲、南丫岛的机动化出行极少，
  因为岛上靠走路——回归时这些区会被"按人口"严重高估（西南新界 7 倍），但这只影响区内分配，区总量取调查值。
- 调查在 2022 年做，2023 年 2 月才全面通关，所以**调查里几乎没有跨境出行**。
  👉 `pipeline/21` 另加三类：跨境学童 CBS、其他香港居民 CBR、访客 CBV，外部小区在各口岸。
- **沙头角**口岸已关闭，入境处数字为 0，但仍有 84 名学童经中英街过境——不在入境处统计里，按额外人次计入。

### 6.39 heredoc + Python 普通字符串：`\b` 变成了退格控制字符

用 heredoc 写补丁脚本，正则里的 `\b` 先被 shell 吞掉一个反斜杠，再在 Python 普通字符串里被解释成**退格符（0x08）**，
写进了 `pipeline/10`。文件看起来只是少了 `\b`，实际藏着控制字符。
👉 改含反斜杠的代码一律用 Edit/Write 工具；怀疑时用 `od -c` 看原始字节，或扫描全部脚本里 `ord(c) < 32` 的字符。

### 6.40 PDF 表格：数字用空格作千位分隔；手册 PDF 加了密

- 出行调查的表格写成"1 048 739"（= 1048 和 739）。👉 `pipeline/20` 的 `split_numbers()` 穷举所有分组方式，
  只保留能让该行"各目的相加 = 合计"的那一种；多于一种或没有都报错，不猜。
- TPDM 手册是 AES 加密（只防编辑），pypdf 需要额外的 `cryptography` 才能读。👉 改用 Git Bash 自带的
  `pdftotext -layout`（`/mingw64/bin/pdftotext`），不需要装新包。
- 看 PDF 里的图（如大区划分图）：临时装了 `pypdfium2` + `pillow` 渲染成 PNG（**未写进 pyproject**，只作查看工具）。

### 6.41 按区对账会被"时间差"误导：皇后山

东北新界的学生比调查多 20%、人口多 8%。查实是**皇后山 2022 年入伙**：规划署表 15 显示它从 1.85 万人跳到 4.65 万，
调查只计入约八成（去掉皇后山后，本模型的东北新界反而比调查少 31%）。

👉 出行率改为"调查各区自身的出行率 × 全港统一口径系数"，而不是"调查区总量 ÷ 本模型区基数"
——后者会把入伙时间差当成出行行为差。核实过的差异登记在 `pipeline/21` 的 `EXPLAINED`，**必须附核实数据**，其他区照常检查。

### 6.42 小汽车矩阵的"绕行过大"判断随小区合并失效

原来用"人口密度 < 100 的小区"识别山地；山坡碎片并入山下的新市镇后就认不出来了。另外直线距离用的是小区几何中心，
而道路距离从出行中心起算，两者不是同一对点。
👉 `pipeline/17`：直线改用 `zone-centres.parquet`；山地改为"离任何楼宇 200 米以外的陆地"（100 米网格）。
剩下 13 对"需人工核实"已逐一核实，**全部与太平山顶 181S 有关**（山顶到华富、田湾没有公共道路直接下山，
薄扶林水塘道不对公众开放，只能绕湾仔峡、深水湾，约 12 公里），属地形。

### 6.43 2022 年的就业人口不能在 2021 与 2026 之间直线插值

直线插值跟不上皇后山这类入伙跳增，东北新界的每名就业者上班出行一度算成 1.91（调查口径最高 1.57）。
👉 2022 年的人数跟随当年人口，只让"就业者占人口的比例"在两年之间平滑变化。

### 6.44 只试"直线最近的一个车站"，会把愉景湾接到一个走不过去的小码头

小区中心改为出行端点加权后，愉景湾的中心离北面一个小码头直线 470 米，但步行要半小时以上，
于是整个小区被改用这个班次很少的码头作起终点，还给所有进出行程补了 35 分钟：到中环 103 分钟（原 68）。
粉岭 620S 同样从 79 分钟变成 138 分钟。

👉 `pipeline/18` 的 `access_points()` 改为试**最近的 8 个车站位置**（同一路边的多个营运商站点算一个）：
任何一个能在 30 分钟内往返，就不动；都不行，才改用**步行最短**的那个（不是直线最近的）。
试算 11 个小区后，需要改用车站的只剩西贡白沙湾 823。
教训：**改了上游（小区中心），下游的规则可能在新输入下失效**——每次上游变动都要把"最极端的小区"重新看一遍。

### 6.45 调查里的出行时间是"自报"的，不能直接当重力模型的目标

第二步初稿把衰减参数 β 校准到调查的平均出行时间（上班 48 分钟 × 45/42）。上班出行的 β 被压到下限（几乎不衰减），
过海出行占 29%（调查 15.9%），各区自给率只有调查的三分之一到一半。原因：**完全随机地分配**上班出行，
引擎算出的平均公交时间也才 50.8 分钟——受访者自报的时间包含找站、挤车和余量，比引擎的门到门时间长。

👉 `pipeline/22` 把目标除以一个换算系数 r（各目的共用，保留调查 48:39:36 的相对长短），
再加一个过海系数 K（按调查过海占比反解），r 取让表 3.4 其余四项 + 表 3.5 十区误差最小的值（黄金分割搜索）：
r = 1.28、K = 0.62，两表均方根误差 4.1 个百分点。
- 表 3.5 的"进出该区的出行"试了三种算法："起点或终点在区内都算一次"误差 4.8，另两种 14–15——定义已核实。
- Gamma 型衰减（c^-α·e^-βc）几乎没改善（4.11 → 3.83），所以没有采用。
- 剩下的沙田马鞍山偏差，规律是**铁路离九龙近的区都偏低**（沙田 去九龙/区内时间比 1.74、荃葵青 1.78 偏低；屯门 2.59 对得上），
  最可能是矩阵里没有东铁/屯马线的拥挤。

### 6.46 方式划分的三个陷阱

- **小区的"公营住户"只有公屋**（普查 80.7 万户 ≈ 统计处公屋 81.7 万户），"私营"只有私人永久房屋；
  资助出售房屋和临时房屋（约 45 万户）没有单独成列，要用"住户总数 − 公营 − 私营"得到。
- **按住户算有车比例会让私家车份额对不上**：调查中其他目的的私家车占 20.5%，而有车住户只有 17.2%。
  大家庭更常有车（表 4.2：1 人户 7%，5 人及以上 35%），**住在有车家庭的人占 21.2%**——按人口加权后四个目的全部对上。
- **同时拟合"时间敏感度"和"无可替代者比例"会走偏**：第一次拟合出 0.275/分钟、36% 无可替代，各方式常数跑到 −19、+29。
  改为只拟合一个敏感度（0.062）。另外，表 5.2 的"改用其他方式"包括公共交通内部转换（巴士改港铁），
  主方式模型看不到这一部分，所以第四步要用实测车流量再核一次。

### 6.47 实时车流：一截一截的色块 → 连续渐变线；探测器方向字段互相矛盾

发起人 9/18 指出实时车流"不美观"、取消勾选后线还在。
- **旧做法**（`pipeline/06`）：每个探测器吸附到最近的街道，前后各取 250 米单独着色，再凭方向名粗略左右错开 5 米
  → 碎段互相叠压。
- **新做法**（`pipeline/15b`）：沿有向路网把相邻探测器连成连续的线（下游 ≤2.5 km、绕行 ≤1.35 倍、转向 ≤120°），
  每个顶点记住前后两个探测器及位置比例，浏览器先插值拥堵程度再上色 → 渐变；两个方向各靠行车方向左侧画
  （deck.gl `PathStyleExtension` 的 offset，单位是线宽，任何缩放都不重叠）；线下垫半透明白色描边。
  807 个探测器中 773 个连进 114 条线，6 个无法吸附的显示为点。**探测器之间的颜色是插值，不是实测**，图例和悬停提示都写明了。
- **勾选框**：原来取消勾选只是停止拉数据，旧数据照画；现在关闭即不生成图层。
- **坑：探测器的罗盘方向和路名里的"北行/南行"有 10 个互相矛盾**。双程快速路两边车道只隔几十米，按错的方向会吸附到对面车道，
  串出"北行→南行→北行"。在只有单行路的位置两者准确率都约 95%；矛盾的 10 个里，路名与同编号系列一致（如新田公路 90073–90085 全是北行，
  唯独 90081 罗盘写"南"）→ **矛盾时以路名为准**，另加"路名方向相反不得相连"的保险。
- 截图检查：`node frontend/scripts/check-traffic.mjs map-check/traffic`（全港、九龙近景、沙田、叠交通分区、关闭图层五张）。

### 6.48 车道数：运输署没有，OpenStreetMap 有；探测器是独立的尺子

- 运输署路网 17 个图层逐一查过，**没有车道数**（只有巴士专线 251 段、路边泊车位 37,267 个）。
- OpenStreetMap 的 `lanes` 标注按长度：快速公路 98%、干线 98%、主要道路 97%、次要 97%、支路 89%、住宅街道 49%、屋苑内部路 13%。
- 匹配规则（`pipeline/15` `add_lanes`）：运输署路段中点 12 米内、走向平行（±30°，同向或反向）的最近 OSM 道路；
  OSM 单行 → 车道数即该方向；双向 → 优先 `lanes:forward/backward`，否则总数对半分。两图单行方向相反 227 段（记录在审计 JSON）。
- **通行能力的出处**：TPDM 第二册表 2.4.1.1（文字版排版错乱，是渲染成图片后读的）。每车道约：快速公路 1,500–1,575、主要干路 1,250–1,400、
  区内干路 850–1,000、地方道路 400 辆/小时——同样一条车道相差近 4 倍，所以**等级和车道数都要**。
- 核对不能自己验证自己：15b 吸附探测器只按距离和方向，**不参考车道数**；用探测器实测车道数修正附近主线，留到第四步校准时再做。
- 表 2.4.1.2：重型车超过 15% 时设计流量要再打折（15–20% 减 7%，20–25% 减 10%），第四步加货车后要用。

### 6.49 图表里的数据可以从 PDF 矢量图形直接读，不必目测

出行调查图 3.3（逐时出行比例）没有对应表格。PDF 里它是矢量图：每个目的是一块填色多边形，上沿就是 24 个小时的累加值。
`pipeline/20` 的 `hourly_profiles()` 用 pypdfium2 读路径坐标，再用图上 7 条网格线（2%–14%）做最小二乘定比例。
**坑**：x 轴刻度线和"非家"用同一个深蓝色——只认**闭合**的多边形，否则刻度线会冒充数据（第一次跑出负数，被自检抓到）。

### 6.50 的士行程太短：整笔车资按平均时间价值折算会把的士挤到超短途

第三步初版的士平均只有 2.5 公里（71% 在 3 公里内）。两个独立来源都说实际更长：普查核心站的士占（私家车+的士）车流 25%（模型 10%）；
立法会参考资料摘要（的士加价，档号 TLB CR 1/5581/00，附件 B 的营业收入 + ISSH03/2025 的日均乘客 72.9 万）推算每程约 6–7 公里。
👉 加一个参数"的士车费权重"（坐的士的人时间价值更高、同行分摊车资、部分公司报销），拟合普查车公里占比 → 0.35，平均 5.8 公里。
与时间敏感度交替拟合到都不动（3 轮，15 分钟）。运输署的"咪表读数调查"才有真正的行程分布，但不公开。
另注意：出行调查的士乘车 83.8 万/日，运输署 2022 年日均乘客 71.1 万——前者是工作日、可能含网约车，暂以调查为准。

### 6.51 车站要吸附到"路段"而不是"最近路口"

巴士预载第一版把车站吸到 150 米内最近的路网节点，观塘道的车站被吸到隔一条街的牛头角道，一小时 497 班巴士——假的。
👉 改为吸附到 25 米内的路段（双程分隔道路两边都保留，按最短路自动挑对的一边），站间路径含终点路段、不含起点路段，避免同一班车在车站路段数两次。

### 6.52 普查站比对：同一条路常被画成几条并行车道

金钟道东行在路网里是两条并行路段（一条 294 班巴士、一条 22 班），夏悫道西行两条相隔 17 米；东区海底隧道两条管道相距超过 30 米。
只取最近一条会严重低估（巴士核对一度只有 0.44）。
👉 `pipeline/15c`：先按普查路名（"RD"→"ROAD"，忽略空格）匹配，在站点横切一条 ±40 米断面线，把同名同向被切到的路段**全部**算进这个方向；
距离用真实中心线（隧道路段长达数公里，端点连线会偏离数百米）。新路在路网里用所属公路的名字（昂船洲大桥=青沙公路、龙山隧道=香园围公路、
将军澳—蓝田隧道=将蓝公路），按最近路段配对是对的。

### 6.53 周年交通普查每个站 Excel 里的宝藏

除了已用的 AADT、高峰小时，每个站的主表还有：**逐小时流量占全日比例**（第 11 列是周一至五，已用"× 双向 AADT = 高峰小时流量"核对，
99% 的站误差 < 2%）、**T-%（高峰小时重型车比例：中重型货车 + 巴士）**、月份和星期系数、2005 年起的历年 AADT；
核心站还有 "OCC" 表（逐小时 10 种车的比例和每车人数）。列标签只画在图上、单元格里没有，列的含义是用数据反推并核对过的。

### 6.54 Git Bash 的 heredoc 又吞了反斜杠（6.39 再犯）

用 heredoc 写的补丁脚本里 `"\n"` 变成换行、断言失败（幸好补丁先检查全部替换再写文件，没有写坏）。
👉 **补丁脚本一律用 Write 工具写**。

### 6.55 探测器不能只按"最近的路"吸附，要用它自己报的路名把关（`15d`）

第一版 `pipeline/15d_speed_profiles.py` 只按"30 米内、走向一致"把探测器吸到路段上，结果算出
"支路限速 50 → 凌晨 78 公里/小时"、"限速 30 → 早高峰 44 公里/小时"。原因：装在快速公路上的探测器
被吸到了旁边平行的辅路，于是把辅路那一类的车速比例整体抬高。
👉 探测器的 `road_en` 里自带路名（`"Wong Chuk Hang Road near ... - Eastbound"`），取 " near " / " - " 之前的一段，
和路段的 `street` 归一化后比对；**只有路名对得上的 706 个（共 800 个）参与推算同类道路的比例**，并对
"实测 ÷ 限速" 设上限 1.25。修完各档比例都落在 0.83–1.08，合理。

### 6.56 分配校准之前，先分清"路线选错"和"普查站配错"

`27` 逐站 GEH 只有 16%，第一反应是"司机对收费太敏感"。真查下去是三件不同的事叠在一起：
1. ~~**青朗公路有 85 条同名路段**，`15c` 配到了一条只有 351 辆的匝道~~——**这条我判断错了，已作废**。
   当时看到"同一条路上别处有 4,685 辆、配到的那条只有 351 辆"就怀疑配对，但收费权重标定后
   同一条链路变成 4,421 辆（实测 3,563）。**配对是对的，错的是模型。**
   👉 教训：**"模型和实测差很多"不等于"对照配错了"**。要先问"如果对照是对的，模型错在哪"，
   能解释得通就不要动对照。动对照是最危险的一种自欺。
2. **支路（LOCAL DISTRIBUTOR）模型/普查只有 0.23**，但这不是错：455 个分区、每区 2.8 条接驳线，
   "最后一公里"被接驳线抽象掉了，宏观模型本来就不该在支路上达标（干诺道 933 辆 vs 模型 14 辆）；
3. **过海通道是真的错**：模型 22,564 辆 vs 普查 17,498 辆（1.29 倍），而且分流完全反了——
   西隧（贵 20 元）实测最多 6,904 辆、模型只有 1,662 辆。
👉 结论：**GEH 全网 85% 这个指标对 455 分区的宏观模型本身就不合适**，应改为"走廊 GEH<5 ≥ 60%"
（已写进 `27` 的 `CORRIDORS`），并且支路站要单列不计入。

**标定后（收费权重 0.20）的实际结果**：走廊 GEH<5 从 6% 升到 35%，其中屯门—荃湾走廊 0% → **80%**，
快速公路 19% → 31%、主干道 15% → 28%。剩下没达标的集中在过海（1.29）、狮子山（1.53）、
青马大桥（0.63）三处，病因已按车种查清（见 6.59）。

### 6.57 收费权重是弱杠杆，过海分流的病根在需求和排队

在 `27` 加了 `TOLL_WEIGHT`（环境变量可覆盖，用于标定），扫了 1.00 / 0.60 / 0.35 / 0.15：
红隧流量几乎不动（12,617 → 11,887），大榄隧道从 499 涨到 930（目标 3,563），走廊 GEH<5 始终 6%。
原因想清楚了：**普查说三条过海隧道实际都没超通行能力**（红隧双向 5,319 辆 / 双向能力 6,000），
是靠"接线排队"把人挤到西隧去的；BPR 曲线在 v/c=2.4 时只加 3.4 倍延误（约 +7 分钟），
而红西隧收费差 20 元 ÷ 私家车时间价值 1.26 元/分 = 15.9 分钟，所以模型怎么调权重都要走红隧。
👉 真正的病根有两个，都是**结构问题不是参数问题**：(a) 出行分布在 `22` 里只有一个不分方式的过海折减
K=0.62，小汽车看不到隧道收费，所以过海小汽车需求本身就多了 29%；(b) 分配没有排队/容量硬约束。
要不要修，取决于方向——见 `docs/architecture-walkthrough.md` 第七节。

### 6.59 香港的隧道费是**乘客**付的，的士的广义成本里漏了这一项

按车种拆开逐站比对后，问题一下子清楚了（模型/普查，8-9 时两方向）：

| | 合计 | 私家车 | 的士 | 旅游巴/私家小巴 |
|---|---|---|---|---|
| 红隧 | 1.91 | 1.24 | **6.84** | 10.53 |
| 狮子山 | 1.53 | 1.50 | **4.02** | 3.12 |
| 东隧 | 1.26 | 0.97 | 2.53 | 3.37 |
| 西隧 | 0.83 | 0.62 | 0.88 | 2.27 |
| 大榄 | 1.24 | 1.30 | 0.64 | 6.51 |

**的士专挑便宜的隧道钻**：红隧（私家车 40 元）6.84 倍，西隧（60 元）0.88 倍。
原因：`23` 里的士的广义成本是 `车内时间 + 权重 × 车费`，**没有隧道费**。
运输署的士车资页写得很清楚：乘客要另付隧道费，**过海还要加一程回程费**——
红/东/西隧各 25 + 25 元、大榄 28 元、大老山 20 元、香港仔/城门/狮子山 8 元。
👉 已改成 `权重 × (车费 + 隧道费)`。用的是矩阵里现成的私家车隧道费（红/东/西 40/40/60、大榄 45），
和乘客实付（50/50/50、28）差在四分之一以内，没有为此再跑一次路径矩阵，已在脚本说明里写明。
**效果**：的士车费权重重新拟合 0.35 → 0.31（车公里占比仍是普查的 25.4%），红隧的士从 6.84 倍降到 **2.36 倍**，
大榄 0.64 → 1.01、大老山 1.01 → 0.95；**过海走廊模型/普查 1.29 → 1.12，GEH<5 从 0% 到 33%**。

### 6.60 分配里五类车原来都按私家车的隧道费算

运输署的收费表是**按车种**的：分时段收费的四条隧道只分 MC / PC / TA / OTH，固定收费的大老山则细到
LGV / MGV / HGV / LB / SD / DD。原来 `15` 只取 PC 一列，`27` 五类车共用一个 `toll` 字段。实际差别不小：

| | 私家车 | 的士 | 轻型货车 | 中重型货车 | 旅游巴 |
|---|---|---|---|---|---|
| 红隧 / 东隧 | 40 | **50** | 50 | 50 | 50 |
| 西隧 | **60** | **50** | 50 | 50 | 50 |
| 大榄 | 45 | **28** | 43 | 43 | 43 |
| 大老山 | 20 | 20 | 24 | **28** | 29 |

👉 `15` 现在按 `TOLL_CLASSES` 逐类取费并写出 `toll_{类}_hkd` 五列，`27` 每个 `TrafficClass` 用自己那列。

的士就只按时间选路了，这正是实测的样子；**商用车在三条过海隧道统一 50 元**，比私家车的西隧 60 元便宜。

### 6.72 配额联动是第一个正面结论：的士车队有三成余量，所以"换牌"几乎免费（`34_scenarios.py`）

6.70 的结论是"加车没用"。顺着它往下问：那**成对的杠杆**行不行？`34` 跑了两种。

**① 夜间窗口**（同样车队，只在 22:00–06:00 接客）——**结论分化，这本身是发现**：

| | 夜间时段接走区内 | 全天运营同规模 |
|---|---|---|
| 观塘 1,200 辆 | **14.9%** | 6.7% |
| 观塘 300 辆 | 7.1% | 1.6% |
| 离岛 1,200 辆 | 3.9% | 10.1% |

**密集市区打时间差有效（观塘翻倍以上），偏远区无效（离岛反而更差）**——因为离岛夜间需求本来就极少。
这条推翻了我之前"夜间是无人车的空间"的笼统说法：**要看哪个区**。

**② 配额联动**（无人车进 N 辆、的士牌同时退 N 辆，总车辆数不增）——**这是这个项目第一个正面结论**：

| | 区内等待 | 全港等待 | 放弃单数 | 总车公里 |
|---|---|---|---|---|
| 今天（17,695 辆的士） | 2.89 分 | 2.05 分 | 63 | — |
| 离岛换 1,200 辆 | 2.33 分 | 2.06 分 | 55 | +0.06% |
| **离岛换 2,400 辆** | **2.16 分（−25%）** | 2.09 分（+2.4 秒） | 51 | +0.29% |
| 观塘换 2,400 辆 | 2.11 分（−12%） | 2.14 分（+5 秒） | 59 | +0.74% |

**退掉 2,400 张的士牌、换成集中在一个区的无人车，那个区等待改善 25%，全港其余地方几乎没感觉。**

**为什么成立**：`31` 已经算出全港 12,000 辆就够（比领牌的 17,695 少 32%）。
**车队本来就有三成余量，所以抽走 2,400 张牌几乎是免费的**；而把这些运力集中到一个区，那个区明显受益。
两个结论是同一枚硬币的两面——没有 6.67 的车队曲线，这个结论解释不了。

**必须一起说的限制**：无人车被限制在区内，所以它只能帮那一个区；全港其余地方是**净损失**
（等待 +2.4 秒、+5 秒），只是小到可以忽略。观塘的代价比离岛大（+5 秒 vs +2.4 秒），
因为观塘的的士本来就更忙。

### 6.75 司机的休息比电池贵——模拟器 v2（`35_duty_and_charging.py`）

到 9/24 为止所有车队数字都出自"车 24 小时不停"的假设，所以它们是**下界**。
这一步把两种停车放进去，量出下界离真值有多远。**两者机理不同，不能共用一个参数：**

- **司机换更**：时间驱动。两班制的士每天约 4 小时不在路上（交更、吃饭、休息）。
  **关键证据**：普查的逐小时的士车流从 7 点到 22 点平得出奇（1.2–1.4 倍日均），
  **16–17 点没有任何塌陷**——说明香港的交更是各车错开的，不是集中时刻。
  所以模型让**每辆车在自己的随机时点休息 240 分钟**，而不是全队同时停。
- **电动充电**：里程驱动。跑满续航就地停充，**忙区的车比闲区的车充得频繁**，这正是它无法并进换更参数的原因。

**结果（接单率 ≥95%、平均等待 ≤5 分钟的最小车队）**：

| 规则 | 最小车队 | 相对不休息 |
|---|---|---|
| 不休息（旧假设） | 12,000 | — |
| **司机换更** | **14,000** | **+17%** |
| **电动充电**（300 km / 45 分钟） | **12,000** | **+0%** |

**司机的休息比电池贵。** 充电在 12,000 辆这个规模上一辆车都不多占——最忙一小时只有 10% 在充。
续航敏感性：200 km 时 12,000 辆仍有 99.1% 接单率、4.6 分等待；300 km 和 450 km 结果相同。
**续航超过 300 公里就不再是约束。**

👉 **对外叙事因此可以拆得更干净**（比笼统的"少 32%"有力）：
- 今天 17,695 辆有司机的的士 → **中央调度后 14,000 辆**（省 21%）
- 再去掉司机的休息 → **无人车 12,000 辆**（再省 14%）

**两个建模上的坑，都记下来：**
1. **离线计数一开始算出负数**。原因：`off_now` 在每分钟开头累加当分钟的增量，
   而"开始休息"的 +1 是在那一分钟处理过程中才写进去的——**加号永远不生效**。
   👉 当场发生的变化要直接改计数器，只有未来的变化才能排进增量表。
2. **"充电次数对不对"一开始我定了个 15% 的容差，是拍的**。改成推理式：
   每辆车每跑满一次续航充一次，收工时还差一点不充，所以次数必然落在
   `[里程推算 − 车队数, 里程推算]` 之间。**能用推理就别用容差。**

### 6.76 别对二进制文件做四舍五入——它不省空间，却会破坏列之间的恒等式

Codex 写的跨文件测试（`tests/test_demand_and_consistency.py`）一上来就红了两项：
`29` 的 `busy_taxis` 与 `veh_min / 60` 差 0.05、`on_road_at_55` 与 `busy_taxis / 0.55` 差 0.118。

查下去是 `hourly.round(1).to_parquet(...)`：**几个列是互相推导出来的**，
存盘时一起舍入到 0.1，恒等式在小数点后第一位就破了。改成 6 位仍差 1.4e-6（除以 0.55 会放大误差），
最后**整个不舍入**。`31` 的 `empty_share` 同理，也去掉了。

👉 **parquet 是二进制的，舍入既不省空间也不提可读性，纯是给自己挖坑。**
这已经是这个工程第三次栽在同一件事上（`31` 的 `empty_share`、`29` 的两列）。

### 6.73 汇总指标会把荒谬结果平均掉——逐站逐车种展开才看得见（`diagnose_corridors.py`）

9/23 我给的士单独设了收费权重 1.0（其余车种 0.20），理由是"的士的每公里成本本来就在计价表里"。
**方向没错，但做成 0.20 对 1.00 的硬性对立，制造了七倍落差**：

| | 狮子山隧道 8 元值多少分钟 |
|---|---|
| 私家车 | `8 × 0.20 ÷ 1.26` = 1.3 分钟 |
| 的士 | `8 × 1.00 ÷ 0.87` = **9.2 分钟** |

后果：**的士全跑去走免费的大埔公路翻山**。普查站 4201 两个方向分别是
「2,670 辆的士 vs 43 辆私家车」和「1,684 vs 10」——**一条 98% 是的士的干道**，现实中不存在。
同时狮子山隧道的私家车变成 1.67 倍（它们不怕那 8 元）。

**我当天自己跑完 `27` 没看出来**，因为我只看汇总：走廊 GEH、车种比值 1.18。
1.18 这个数把"某些站 20 倍、某些站 0.1 倍"平均成了"略高"。
是 `diagnose_corridors.py` 逐站逐车种展开才暴露的——**这个工具第一次运行就抓到它**。

👉 **教训一**：**汇总指标是用来确认没问题的，不是用来发现问题的。** 一个 1.18 的比值背后
可能是一堆互相抵消的荒谬。改完模型必须跑逐站展开。
👉 **教训二**：给某一类车单独设参数时，**要算一下它和别的类差了几倍**，而不是只看自己那一项的道理。
**标定扫描的结果：把这个特例删掉。** 扫 0.20 / 0.35 / 0.50 / 0.75，
「的士占比 >50% 的路段方向」数目是 **182 / 314 / 425 / 464**——**完全单调**，权重越高越糟；
走廊 GEH<5 也是 0.20 最好（29% vs 其余 18%）。所以 `CLASS_TOLL_WEIGHT` 已删除，
的士和其他车种用同一个权重。

**修复效果**：大埔公路 4201 站的士占比 **98% → 32%**（私家车 43 → 971、的士 2,670 → 456）；
走廊 GEH<5 23.5% → **29.4%**；的士车种比值 1.18 → **1.14**；狮子山 25%、红隧 20%（全港均值 28%）。
全网 GEH 18.8% → 15.7% 是微降，**这个交换我接受**：用一个荒谬的局部结果换来的统计改善不算数。

👉 **要分清两件事**：分车种的**法定收费**（的士过海 25+25、货车按 OTH）是真实数据，**保留**；
分车种的**权重**是我的发明，**删掉**。
👉 已把「任何路段的士占比不得超过 50%」加进 `27` 的常规核对（容许 200 个，当前 182）。
👉 **教训三**：一个局部正确的论证（"的士的每公里成本在计价表里"）**不保证在系统里是净改进**。
判断标准是整体指标，不是这条论证本身有没有道理。

👉 **另一件被这次纠正的事**：我曾以为改 `27` 要重跑整条产品链。**不用**——
`28`–`34` 全都不读分配结果，它们用**自由流矩阵 × 探测器实测的逐小时拥堵折算**。
这是有意的设计，也更可靠：实测车速比模型自己算出来的拥堵时间可信，这正是行车时间能做到 12% 误差的原因。

### 6.71 派单循环抽成了共享模块（`fleet_sim.py`），并证明产出逐值不变

`31`（全港单车队）和 `32`（区域双车队）原本各有一套重复的分钟级派单循环。
再加两个情景就是第三、第四份——**一个循环的 bug 要改四个地方**。

抽出 `pipeline/fleet_sim.py`（不带编号，它不是管线的一步）。关键是**发现"车队"只有三个字段**：

```
size   多少辆
area   能在哪些分区【接客】（None = 全港）。不限制停在哪——车停在乘客下车的地方，
       区内区外都可能，这个漂移是区域牌照的真实问题，模型不该掩盖
hours  能在哪些小时接客，[start, end)，跨午夜就写 (22, 6)
```

一支车队、不限区、全天 = `31`；两支、一支限区 = `32`；夜间服务只是改 `hours`；配额联动只是改两个 `size`。
**新情景不再是新代码。**

**回归证明（这一步不能省）**：先把重构前的产出存成快照，重构后逐列比对——
`31` 全部 10 列**最大差 0**，`32` 全部 16 个数值列**最大差 0**，文本列一致，
Codex 写的 10 项检查全过（含第 1 条"纯的士独立路径"）。

两个细节差点被我弄丢，记下来：
1. **`max_wait_min` 我一开始置零了**，回归立刻抓到。模块里补了最大等待的记录。
   👉 **重构时"这列没人用"不是省略它的理由**——回归比对会告诉你有没有丢东西。
2. **第 1 条检查靠一条"纯的士"的独立路径**。如果我图省事让它变成"两支车队、其中一支为 0"，
   这条检查就退化成自己和自己比。所以给模块加了 `watch` 参数：**观察区和车队的执照区解耦**，
   单车队路径也能报区内统计。👉 **别为了少写代码把别人的验证条件弄没了。**

代价：`32` 从 169 秒变成 420 秒（逐车队循环比写死两支慢）。7 分钟可接受，将来要提速就在模块一处改。

### 6.70 区域投放情景的结论是负面的，而这正是它有价值的地方（`32_deployment_scenario.py`）

`32` 让两支车队在同一份需求上竞争：无人车**只能接起点在投放区内的单**（现实里运输署发的就是
有地域限制的牌照），的士照常全港运营。投放区选离岛（东涌+机场）和观塘，无人车扫描 0/100/300/600/1200 辆。
Codex 实现，10 项自查全过、两次运行逐值一致；我独立重算过结果表，数字一致。

**结论：往今天这个市场里加无人车，几乎什么都不会发生。**

| 区域 | 无人车 | 接走区内行程 | **利用率（最忙一小时）** | 区内等待 | 总车公里变化 |
|---|---:|---:|---:|---:|---:|
| 离岛 | 100 | 1.7% | 34.7% | 2.83 分 | +0.01% |
| 离岛 | 1,200 | 10.1% | **13.7%** | 2.26 分 | −0.25% |
| 观塘 | 1,200 | 6.7% | 23.7% | 2.24 分 | +0.09% |

原因：17,695 辆的士已经铺满全港，派单时**永远有一辆的士离乘客更近**，无人车抢不到单。
1,200 辆车最忙的一小时也只有 14% 在跑，等待只降了 36 秒。

**区域牌照的漂移也很严重**：离岛 91–99%、观塘 **100%** 的无人车全天最大占比停在投放区外——
送完客出了区，只能干等区内的单。这一条是我在任务书里刻意不让模型掩盖的，结果比预想的还难看。

👉 **这个负面结论比正面结论有用**：它说明"投放 N 辆无人车"本身不是一个政策，
往饱和市场加运力等于让资本闲置。真正的杠杆必须成对，而数据已经指出往哪走：
1. **配额联动**——无人车进、的士牌退；`31` 的车队曲线能算"退多少还不塌"；
2. **打时间差**——凌晨 3 点只有 5,369 单，的士供给也薄；
3. **打空间差**——离岛正是车队缩小时最先被放弃的地方（6.67），本来就供给不足。
第 2、3 条用现有代码就能算，改动很小（限制无人车的运营时段 / 运营分区）。

### 6.69 "地图上那几个小圆点"——不是残留，但界面没说清楚就等于是残留

发起人看到地图上几个孤零零的黄色圆点，第一反应是"前面剩下的没擦干净"。查下去：
那是 `live-traffic-points` 图层，画的是 **`15b` 没能并进任何走廊线条的 6 个探测器**
（康庄道近理大、东区走廊近爱蝶湾、粉岭绕道、大老山公路、青朗公路近锦上路站、新清水湾道）。
它们都有实时读数，位置也都对——**数据是真的，但一个点旁边没有线，看起来就是垃圾**。

再追下去，发起人指的其实是**两种**东西，第二种是真缺陷：

**① 红磡那个大橙点**：`15b` 没能吸附的 6 个探测器之一（康庄道近理大）。位置对、数据真，
但 `detectorRadius` 让点随车流长大到半径 10 像素，一个高流量的孤点就成了一块橙色圆饼。
我先后两次把半径调小（10.5 → 6 → 4.0 像素），发起人两次都说"还是饼"——
**因为只要它比线条粗，读起来就是异物，调参数救不了**。
👉 最终按发起人的决定：**把孤立探测器的圆点图层整个去掉**（`live-traffic-points`），
只留线条。代价是 34 个探测器的读数不在图上显示，收益是视觉语言只剩一种。
图例改成解释"为什么有些路没有线"，而不是解释那些点是什么。

**② 瀝源那种小点**：`15b` 造出了 **28 条"只含 1 个探测器的走廊"**（共 114 条），
按 `END_M=250` 在它前后各画 250 米路，城市尺度下就是一小截粗线头——看起来就是个点。
**一个探测器不成走廊**，而且这样画等于宣称"这个读数沿这段路都成立"，实际上我们只知道那一个点。
👉 `15b` 里把它们并入 `unmatched`，和吸附失败的一起画成点。
结果：走廊 114 → **86 条（每条都连起 ≥2 个探测器，覆盖 97% 的探测器）**，单点 6 → 34 个。
视觉语言统一了：**线 = 可沿路插值的路段，点 = 只知道这一个位置**。

👉 教训：**凡是"只有一个"的东西，界面必须解释它为什么只有一个**，否则用户会当成 bug。
已在实时车流图例加一行说明（数量从数据读）。

👉 还有一条操作教训：截图自检完不要用 `taskkill /F /IM node.exe /T` 关服务器——
它会杀掉机器上**所有** node 进程，包括发起人自己开着的那个（已经误杀过一次，
表现为"怎么没有车流"）。按端口关，或者干脆留着。

👉 顺带又踩了自己刚写下的坑（6.65 最后一条）：我第一版把"共 6 个"写死在 tsx 里，
`15b` 一重跑就过期。已改成从 `detector-corridors.json` 的 `unmatched.length` 传进去。
**给字面数字 = 写死，这条对我自己一样成立。**

### 6.67 车队模拟器跑通了（`31_fleet_simulator.py`）——头条数字是"少三成车"

**这是第一个"结论不是标定出来的"步骤**：车队规模、等待时间、空驶里程都是需求和路网推出来的后果，
所以它能被 `29` 的独立边界反过来检验（核对三：模拟最忙一小时 11,291 辆在跑，
`29` 只算载客时间是 9,216 辆，差 +23%，多出来的正是接客空驶和上下客时间——量级对）。

**基准（车队 17,695 辆 = 今天的领牌数）**：接单 100%、平均等待 **2.1 分钟**、空驶占 **14.3%**、
最忙一小时 11,291 辆在跑（占车队 64%）。

**车队规模扫描（同样的 717,198 单；2026-09-24 按最新需求重跑）**：

| 车队 | 接单率 | 平均等待 | 空驶占比 |
|---|---|---|---|
| 17,695（今天） | 100.0% | 2.1 分 | 14.3% |
| 14,000 | 100.0% | 2.2 分 | 15% |
| **12,000** | **100.0%** | **2.4 分** | **16%** |
| 10,000 | 99.1% | **6.0 分** | 19% |
| 8,000 | **87.9%** | 15.8 分 | 22% |
| 6,000 | 68.2% | 15.9 分 | 23% |

👉 **接单率 ≥95% 且平均等待 ≤5 分钟的最小车队是 12,000 辆，比今天少 32%。**
8,000 辆时服务崩塌（接单 87.9%、等待 15.8 分），所以真正的悬崖在 10,000 和 8,000 之间。

**必须一起说的四条局限**（不说就是骗人）：
1. **没有再平衡**：车送完客就在原地等。这对等待时间是悲观端、对空驶里程是乐观端。
2. **车不休息**：没有司机换更、没有吃饭，无人车也没有充电。**这是最大的乐观项**，
   所以 12,000 是"无充电约束下的下界"，真实的无人车队要更多。
3. **需求是固定的**：等待从今天的水平降到 2 分钟必然会拉来新需求，模型没有这个反馈。
4. **分区级、不是路段级**：接客距离用的是分区间矩阵，同区内的接客算作 0 距离。

**空驶的对比要小心口径**：模拟的 14.3% 是"调度车不巡游、只在原地等派单"；今天的巡游的士按 `29`
夹出来是 15%–35%。所以调度省下的车公里介于 **1% 到 32%** 之间——区间这么宽，是因为今天真实空驶率
还没定死（见 6.66）。**不要只报 32% 那一端。**

### 6.66 空驶率推不出来，但能被夹住——而且夹出来的结论和直觉相反（`29_fleet_supply.py`）

**先说陷阱**：`23` 的平均行程 8.5 公里，本身就是用「普查车公里 ÷ 运输署载客人次」反推的。
**再用两者之差去算"空驶"，是循环论证**——模型当初正是假设两者相等才定出 8.5 公里。
这个坑很隐蔽，差一点就做出一个自欺的数。

**能算准的部分**（`29` 做的）：把 717,198 条请求按自由流矩阵算出载客时间和距离，
再用探测器实测车速做逐小时拥堵折算（8 时 ×1.21、18 时 ×1.17、3 时 ×1.00），得到
**全日载客 597 万车公里、11.7 万车小时；最忙的 8:00 同时有 9,216 辆车载着客**。

**两侧夹逼**：
- **车队容量给下界**：领牌 17,695 辆、高峰假设 80% 在路上 = 14,156 辆可用，
  而 8:00 就要 9,216 辆在载客 → **载客率不可能低于 65%**。
- **日行驶里程给上界方向的约束**：载客率 70% 时每辆车每天跑 482 公里，85% 时 397 公里；
  香港两班制的士实际约 350–450 公里/日，**指向载客率 70–85%**。

👉 **结论和直觉相反，而且对项目定位很关键**：香港的士的载客率**不是**常被引用的"一半空驶"，
而是 **65% 以上**。所以"无人车队消掉大量空驶"**不是这个城市最强的论点**。
真正的论点应该落在：**司机成本**（占运营成本大头）、**夜间与薄需求地区的覆盖**、
以及**配额自 1994 年冻结在 18,163 辆、载客量却十年跌三成**这个结构性错配。

`ON_ROAD_AT_PEAK = 0.80` 是假设，下界只和它一样可靠，已在代码里写明。
要真正定死载客率，需要一个本工程没有的量：每程平均载客人数，或运输署计价表读数调查的载客公里
（2024 年车资检讨文件提到做过这个调查，但没公布数字）。

### 6.64 `28_taxi_requests.py`（叫车请求生成器）：交给 Codex 做、我验收后收进工程

**这是第一个外包给 Codex 又收回工程的脚本**，过程本身有教训，值得写下来。

**它做什么**：把 7 个「分区 × 分区」的的士人次矩阵展开成 **717,198 条带时间戳和上下车坐标的请求**，
覆盖完整 24 小时。产出 `data/model/taxi-requests-2026.parquet`、`data/web/taxi-requests-audit.json`。
这是车队模拟器的输入。

**方法的关键一步**：逐小时曲线**不能用出行调查的时段曲线**。调查曲线是全方式的，早高峰占 9.3%，
而普查实测的士只有 6.0%——直接用会让 8–9 时多出 52%。改成用普查的士人次形状重标定：
`每站全日车流 × 逐小时占比 × 的士占比 × 每车人数`，归一化成 24 小时形状，再按小时整体缩放
（只改各小时总量，不改小时内各目的构成，和 `24` 的做法一致）。
注意 **OCC 表只有 07:00–23:00 共 16 个时段**，缺的 8 小时用最近时段的值外推，已在报告里写明。

**两个必须记住的副作用**：
1. **目的构成被改变了**：HBS 校巴类 −18%、NHB −12.8%，而 HBO +2.2%。因为按小时统一缩放，
   **高峰集中的目的必然吃亏**。绝对量上 HBS 只有 1.7 万条（占 2.4%），可接受，但不能装作没有。
2. 这个形状正比于**人公里**而不是人次（普查数的是流量），若各小时平均行程不同会有偏差，脚本里写明了。

**验收的教训（第 6.65 条专门讲）**：他两次都**把我列的自查换成他自己设计的**，其中一次的替换
正好掩盖了真缺陷。第二次交付 8 项全过，但第 5 项「平均行程」比错了口径——
目标 8.5 公里只统计本地四个目的，他把跨境也算进去得 9.261 公里，**碰巧在 10% 阈值内通过**。
收进工程时我改成同口径，结果是 **8.487 vs 8.500，误差 0.157%**。
👉 **"通过了"和"因为对的原因通过"是两回事**，验收必须自己重算一遍，不能看他的自查表。

### 6.62 的士："趟数多了 44%、每趟短了 30%，乘积刚好对"——所以一直没被发现

**先纠正我自己第一版的结论**：我一开始只看到"模型 974,552 vs 官方 682,000，高 23%"就想直接下修，
这是错的。因为普查（ATC）独立数到的**的士车辆**占早高峰车流 16.0%，模型对得上（1.10 倍）——
砍掉需求会把这个对上的指标弄坏。**两个数字都对，量的是不同的东西**，必须先想清楚再动。

数据：
- **运输署月报表 2.1S**（`data/raw/td-digest/2606_table21s.xls`，2026 年 6 月版）的士平均每日乘客人次：
  2021 **762,328** / 2022 **711,113** / 2023 **727,948** / 2024 **682,646** / 2025 **676,105**。
  这是运输署用**的士营运数据**估的，不是调查。
- 立法会 `ISSH03/2025`：车队约 **18,100 辆**十年不变、平均车龄 8 年；的士占公共交通载客量 7.7% → 5.8%；
  市区牌价十年跌 46% 至 360 万（2025 年 2 月已低于 290 万）。

诊断（这一步是关键）：

| | 模型 | 独立来源 | 结论 |
|---|---|---|---|
| 每日人次 | 974,552 | 676,105（运输署 2025） | 模型高 44% |
| 平均行程 | 5.78 公里 | 反推约 8.3 公里 | 模型短 30% |
| 人公里（乘积） | 5.63 百万 | 5.63 百万 | **对得上** |

**普查只管住了乘积**（`23` 拟合的士车费权重时，靶子是"的士占车公里 25.4%"），所以趟数和行程各错一半、
方向相反，互相抵消，一直没暴露。两个旁证：
- 8.3 公里按市区收费表 = 29 + 66 = **95 元**，接近实际平均车资；5.78 公里只有 69 元，偏低。
- 18,100 辆车 × 每车每日 37 人次 = 676,105，符合两班制；模型的 53.8 人次/车不可能。

👉 **修法（已实施）**：在 `23` 里把的士出行数锚定到运输署的数字（`TD_TAXI_DAILY = 676_105`，
乘工作日系数 1.0418、除以跨境占比 1.172），差额全部计入公共交通；的士车费权重会自动重新拟合，
把平均行程拉到 8–9 公里，**人公里守恒，所以普查验证的车流量不会被破坏**。
`TAXI_TRIP_KM` 合理带相应改成 (5.0, 11.0)，并加了「的士锚定复核」自查（总量 ±5%、跨境占比 ±10%）。

**锚定后的实际结果（9/23）**：本地 570,067 + 跨境 133,627 = 703,694 人次，折回全日 **675,460**，
对运输署 676,105 差 **−0.1%**；平均行程 5.78 → **8.5 公里**；的士车费权重 0.31 → 0.17（未触边界）；
**的士占车公里仍是普查的 25.4%**。方式构成：的士 6.8% → 4.6%，差额进公共交通（73.5%）。

**最关键的一条验证**：早高峰的士车次从 62.0 千砍到 **44.2 千（−29%）**，而普查站上数到的的士
（核心站按车种）从 1.10 只变到 1.19。这证明**普查站数的是"车流"、由车公里决定，与趟数无关**——
我"趟数少、每趟长"的推断成立，不是把一个指标修好、把另一个弄坏。

三重锚定自洽：趟数对运输署营运数据、车公里对普查、行程长度是两者的商
（8.5 公里按收费表约 97 元；折算每辆的士每天 612万÷17,695 ≈ **346 公里**，两班制合理）。

**代价（必须写明）**：走廊 GEH<5 从 35% 退到 18%。的士行程变长后更愿意走隧道和快速公路。
其中一半已经用 6.63 修回，剩下的是 17 个站的小样本抖动（一个站占 5.9%），**不应再调**——
那是对 17 个数字过拟合。剩余误差的结构性原因见 6.56、6.61。

### 6.63 收费权重对的士不适用：隧道费被打了两次折

锚定后的士在每条隧道都超标（大榄 1.01 → **2.57**、红隧 2.36 → 2.66），尽管的士车次少了 29%。
原因是隧道费被打了两次折：`23` 里乘客按车费权重 0.17 感受「车费 + 隧道费」，`27` 里又乘 `TOLL_WEIGHT` 0.20。
大榄隧道对的士只值 `28 × 0.20 ÷ 0.87 = 6.4 分钟`，几乎免费。

👉 `TOLL_WEIGHT = 0.20` 的理由是"替没建模的每公里油钱背锅"，但**的士的每公里成本本来就在计价表里**，
乘客按公里付钱、隧道费另付现金。所以这个折扣对的士根本不该用。
已加 `CLASS_TOLL_WEIGHT = {"taxi": 1.0}`，其余车种维持 0.20。
效果：大榄 5,094 → 4,408、狮子山走廊 1.25 → 1.10、主干道 0.86 → 0.94、快速公路 GEH<5 12% → 19%、全网 16% → 18%。

👉 **这一组数字也是项目叙事的实证基础**：行业十年萎缩近三成、牌价腰斩、车队一辆没少——
而且模型现在能算出**空驶**（普查车公里 − 载客车公里），那正是中央调度的无人车队能消掉的部分。

**车队供给（运输署月报表 4.1(a)，`data/raw/td-digest/2606_table41a.xls` 工作表 `T4.1a(3)`）**：
配额是 1994 年起冻结的，登记数十年不变——市区 15,250、新界 2,838、大屿山 75，合计 **18,163**。
但**实际领牌数在掉**：2021 年 18,061 → 2025 年 **17,695**（市区 14,941 / 新界 2,679 / 大屿山 75）。
也就是 **468 辆有配额却没领牌**（2021 年只有 102 辆）——车主宁可停着也不续牌，又一个行业萎缩的硬证据。
这三个数是"N 辆无人车能顶多少的士"的分母，将来 `29_fleet_supply.py` 直接用。

### 6.61 旅游巴/私家小巴：数量对，但跑得太远

车种比对显示旅游巴在每条隧道都超 2–7 倍，但**全网车次占比 3.9% 对普查 4.1%，是对的**。
说明不是数量问题，是**行程太长**：`23` 里 SPB 的广义成本只有 `车内时间`（没有车费、没有收费），
出行分布又是按目的不分方式做的，于是校巴/员工巴士继承了和小汽车一样的长途分布，
而现实里校巴和屋苑巴士是短程接驳。**待修，属于"方式专属阻抗"这一类结构问题**（和过海小汽车需求偏多同源）。

### 6.58 实测车速反过来证明了分配的"结构"是对的（意外的好消息）

用 589 个"有探测器、又在分配结果里"的路段方向做检验：把实测夜间车速当自由流、早高峰车速当拥堵后，
实测行程时间比随**模型算出来的 v/c** 单调上升——v/c 0–0.4 时 1.06 倍、0.6–0.8 时 1.13、
1.0–1.3 时 1.24、1.3 以上 1.89。也就是说**模型判断"哪里挤"是准的**。
现用 BPR（α=0.15、β=4）预测行程时间的中位误差 **9.1%**，比重新拟合出来的（α=0.36、β=1.30，误差 10.4%）还好。
👉 **BPR 不用改**；对"调度要的行车时间"这个用途，干路网已经达标（目标 <15%）。
注意口径：探测器测的是路段中间的点速，不含路口延误，所以市区街道仍偏乐观。

### 7.1 为什么要有这个

这套方法不是我发明的，是从发起人反复提出的问题里提炼出来的——**他每一次提问都指出了一个真实漏洞**。
第 6 节里超过一半的错误是靠这套方法自己抓出来的，不是靠运气。

### 7.2 硬性检查（写进代码，能自动跑）

见 `docs/data-audit-checklist.md`，共 11 条。前 7 条是可自动化的：

| # | 检查 | 通过标准 |
|---|---|---|
| 1 | **总量比对** | 与官方公布数字误差 < 1% |
| 2 | **空间覆盖** | 覆盖目标范围 > 95%，无整片空白 |
| 3 | **缺失值语义** | 每个字段明确 `-` 是零还是未公布 |
| 4 | **粒度** | 单元大小适合用途 |
| 5 | **几何质量** | 全部有效、无重叠、坐标系正确 |
| 6 | **异常值** | 无不可能值，且每个离群值**能说出名字** |
| 7 | **可复现** | 脚本可重跑，来源网址和日期已记录 |

后 4 条靠人判断，写进交付说明：**实测 vs 估算 / 时效性 / 权威性 / 锁死风险**。

### 7.3 怎么落地

**每个 pipeline 脚本末尾都有一段 `# --- audit ---`**，跑完直接打印中文审计结论，
并写出 `data/web/<name>-audit.json`。

**`pipeline/audit.py` 是总闸**，跨数据集检查 **97 项**，失败返回退出码 1：

```
uv run python pipeline/audit.py
...
```

它检查：跨文件小区编号一致性、几何有效性、除零字段、对官方总量、各管道审计 JSON 无"需复核"项、
路网强连通、接驳覆盖、跨境口岸、ATC 车流量合理性；9/17 新增：
**出行端点**（覆盖全部小区、无负值、各目的产生 = 吸引、机动化总量与调查相差 ≤5%、跨境与入境处一致）、
**小区中心**（全部落在所属小区内）、**矩阵**（小区编号和顺序与土地利用表一致）、
**公交极慢小区**（任何小区的出发或到达中位时间 > 150 分钟即不通过——曾咀那种问题现在会被自动抓到）。

### 7.4 九条实操心法（比清单更重要）

1. **先找官方总量对账，不要做完再解释。**
   这是最有效的一条。几乎所有错误都是在"拿官方数字一比"的瞬间暴露的。

2. **两条独立数据链交叉验证。**
   最强的证据不是单个数字对得上，而是**两条毫无共用假设的链条互相印证**：
   - 规划署 18 区就业 × 楼面回归 → 机场岛约 7.5 万岗位；机管局公布机场社区约 7.5 万人。
   - 出行调查的就业者 vs 普查口径的就业者：26 个区的比值平均 0.965、标准差 0.03——
     稳定的比值说明是**定义差**，个别区偏离才是**数错了**（皇后山就是这样被找出来的）。
   （旧例子"普查固定工作地点 vs 楼面换算岗位差 11%"依赖一组没有出处的每岗位楼面，已于 9/17 撤下。）

3. **任何"合理区间"必须有出处。**
   毛楼面/内部楼面 1.2–1.5（业界使用率 70–80%）、每间客房 60–70 m²、每床 60–200 m²、
   每户 70–90 m²。写进代码常量并注明来由，否则下一个人无法判断。

4. **异常值要查证到能命名原因。**
   "大埔 7.73 倍"不能写成"异常"，要写成"**科学园，政府持有，不计入 RVD 私人存量**"。
   说不出名字就说明还没查清。

5. **结构性风险要主动设想并证伪。**
   例：塔楼会不会和裙楼重复计算楼面？→ 实测 Austin Station 证伪。
   不能因为"看起来没问题"就跳过。

6. **编码字段不要信字面，用外部真值验证。**
   `TRAVEL_DIRECTION` 那次就是教训。找得到外部真值就一定要用（探测器的罗盘方向）。

7. **名称匹配必须防前缀吞并，并加断言。**
   匹配不上的要报错，不要静默跳过。教育局改个名不应该让模型悄悄算错。

8. **区分"我们测不了"和"我们测错了"。**
   校园范围测不了（院校多为租用商业楼层），那就明说它只作**相对权重**，不要假装是楼面面积，
   也不要让一个测不了的指标去触发审计告警。

9. **昂贵的结果先落盘；试跑要走完全程。**
   审计代码本身也会出错。它出错时不应该连带毁掉一小时的计算；
   而一个中途提前返回的试跑，等于没有测试它跳过的那部分代码。

10. **一个概念只定义一次。**
   "哪栋楼是住宅"曾在三个脚本里各写一遍，修一处必漏两处。共用的判断放进上游数据的一列，下游只读。

11. **看结果的分布，不只看合计。**
   全港审计 77 项全过，曾咀的公交中位时间却是 185 分钟——合计和覆盖率都看不出来。
   每做完一步，把"最极端的 5 个小区"列出来看一眼，并把看到的问题变成一条自动检查。

### 7.5 交付任何一份数据时必须一起说的三句话

1. 这份数据覆盖了什么、**没覆盖什么**；
2. 和官方数字差多少、**差在哪**；
3. 哪部分是**实测**、哪部分是**估算**。
