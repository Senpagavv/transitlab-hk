**之前的算法（发起人问「80 和 40 到底怎么分」，这次才讲清楚）**：v2–v4 每个人有一个隐藏门槛（一批人均匀排开），只看比例**最高**的那座站，高过门槛就去，否则开车。80% 和 40% 两座站时，八成的人全去 80% 那边，40% 那边一个人也没有（除非 80% 那边刚好满了）；圈上写的 40% 意思是「只有这一座站时会来 40%」。发起人之前问的「两边距离一样，一边来人一边不来」就是这个原因（一样高时班次密的那边全拿走）。

- 人人都想坐巴士：只要 6 格内、而且比走去市中心近的地方有站，就坐。几座站按吸引力（门口 100%，每格少 10%）**按比例**分：每个人带一个均匀排开的抽签号，落在哪座站的那一段就去哪座站——一批 12 人遇到 80% / 40% 正好 8 人和 4 人，每次都一样（`split()` / `slice()`）。
- 出门那一刻正满的站不算在分流里（其他站按比例分）；附近都满就在家等，约 50 秒还不行就开车（原因「站满了」）。走到站才发现满了：从原地改去别的站一次，不行就走回家，想 20 秒再试一次；**最后一次回来、或在路上耗光耐心的，回到家直接开车**（v4 还要再想 20 秒）。搬站送回家的人不算他们的失败。
- 分数＝坐巴士到达人数；开车的人按原因记。挪站、冷却、倒计时、轮次、上车必送到都和 v4 一样。
- 预测 `forecast()`：每个屋苑分去各站的比例和每轮人数；每座站按真实的出门时间、抽签号、走路时间和发车时刻往后推，算每轮最多同时等几人、有几人会碰到满站。**只算这座站自己**（上一轮没运完、还在排队的人算在内），被挤走的人去哪不算。

**画面（`v5/ui.js`、`style.css`）**
- 每个屋苑到它用的每座站画一条线，越粗人越多，线上写百分比；拖站 / 停在 ＋ 上时线跟着变（虚线是预览）。没有站够近的屋苑写「没有站够近 → 全部开车」。
- 站的红光：淡红＝快满（最多同时等到 3/4），一明一暗的红光＝会爆。开局前看整局最挤的一轮，开始后看这一轮，倒计时时看下一轮。
- 潮汐表右边加三栏：每轮去 A / B / C 站的人数，橙色快满、红色会爆。站的面板写「谁会来（各百分比）」「人最多的一轮来几人、最多同时等几人」「第几轮会爆」。
- 终点叫市中心（不再是港铁），HUD 改成「坐巴士到达 / 开车」。目标进度条只显示过关线附近那一段，三个刻度不再挤在一起。相邻两站的座位格改窄，不再重叠。

**三关（`v5/data.js`，人数用 `bots/v5_sweep.js` 扫、`bots/v5_tune.js` 定）**

### 2026-10-09 18:25 · v4.0 试玩：轮次规则 + 两关新关卡（v3 不动）

**起点**（发起人 10/9）：先不动 v3。复制一份工程，去掉原来的关卡，用新规则做两关让他玩；规则由我细化，把取舍调平衡、调好玩。参考 MDA 论文（Hunicke、LeBlanc、Zubek 2004，<https://www.cs.northwestern.edu/~hunicke/MDA.pdf>）。要求：决策点不要太多、要均衡，要像 puzzle——一定有最优解，玩的时候很难找到，但靠努力和信息能慢慢逼近。

此前的讨论定下的规则方向：
- 要「看预告、提前挪」的规划型。
- 每轮前 3 秒倒计时，不强制暂停，想停就自己停。
- 挪站后有冷却，按游戏时间算，暂停时也停住。
- 每格降 10%。
- 界面不给四区简图，让玩家自己在脑中建图。
- 每关要有排行榜，所以背熟关卡也不能钻空子。

**从 MDA 用到的**：
- 先定想让玩家感受到什么，再倒推规则。这里要的是挑战（有最优解但难找）、发现（自己在脑中建图）、紧张感起伏（需求按阶段推进）、竞争（排行榜）。
- 挑战靠时间压力和清楚的胜负反馈。
- 别让开局一步错满盘输（大富翁的教训），每个阶段都给重新调整的机会。
- 规则数字要好心算。

**规则（`v4/engine.js`，关卡参数在 `v4/data.js`）**：
1. 每轮 2 分钟，各区的人在整轮 110 秒里陆续出门，不是一下子涌出来。这样一轮快结束时站上也有人在用，提前挪就有代价，堵住「在轮尾空档里提前挪、冷却白白走完」的漏洞。
2. 挪站冷却 20 秒（游戏时间），期间不上客，班车按原时刻表照开（空车）。去掉 v3 的「重建完再等一整个班距」。
3. 意愿每多走 1 格少 10%，站要比港铁近。
4. 每班 8 座、排队 8 人，挪站 4 次。班距 = 60 秒 + 到港铁每格 8 秒，所以离港铁远近的取舍比 v3 更明显。
5. 下一轮开始前 3 秒（真实秒，任何速度都是 3 秒）倒计时，显示下一轮各区人数。
6. 暂停时挪的站可以撤销，次数退回；按「继续」后冷却才开始走。
7. 其余规则同 v2.5/v3：满站没人选、就近换站一次、回家想 20 秒、最多出门两次。

**两关**：

**规则**（`engine.js`）——发起人：满人的车站在满人状态下对人没有吸引力；人做决定那一刻如果站是满的，就只在其他站和开车之间选；已经走上去另一座站的路，就算近的站空出来也不回头。实现：`attraction()` 里排队位满 8 人的站返回 0，对所有决定都生效（刚出门、就地换站、回家想完再选）。走在路上的人本来就不中途改道（只有目标站被搬走时才重选）。在家因为最近的站正满而没出门、最后开车的人，开车原因记为「站满了」。

**验证**：`node v2/test_engine.js` 18 项通过（新增：满员的站吸引力为 0、整局没有人选到正满的站、走在路上不改道）；`node bots/evaluate.js v2 --write`：静态 ≥133 的 2 种、≥140 的 0 种。

### 2026-10-06 21:00 · v2.4：回家想 20 秒，再在「最近的站」和「开车」之间选一次；门槛 131 / 140 / 146

**规则**（`engine.js`）——发起人：回到家的人应该待一会儿，再从就近的站和开车里选一个出发。v2.3 有两处不符合：回家的人把刚失败的站排除了（往往就是离家最近那座），以及就地换站也算一次出门、用完就不能再出门。改为：
- 回到家先想 `homeThink` = 20 秒，然后做一次决定：按同一条距离规则（含「比港铁近」）最近的合适站——刚才满的那座也算，他们不知道现在还满不满——就再出门，否则开车。
- 「出门」只算从家里出发，每人最多两次；每趟出门途中最多就地换一次站。所以最多的走法是：出门 → 换站 → 回家 → 再出门 → 换站 → 回家开车，有上限，不会来回绕。
- 第一次在家（刚出门那批）规则不变：最多考虑 50 秒（`homeGrace`），等站建好。

**难度**：回家再出门会救回一些人，静态布局分数上升，前几名挤在 130–132（`bots/curve.js`）。门槛随之定为**过关 131**（286 种静态只有 4 种能过）、**高分 140**（静态最多 132；从最佳静态开局、只会跟高峰挪的机器人 137 也不够；开局把两座站留在南边再跟着挪 143）、**潮汐大师 146**（搜索上限 146–147）。如果要更严，过关可提到 132（只有唯一一种开局能不挪站过关）。

**验证**：`node v2/test_engine.js` 17 项通过（新增：回家后正好 20 秒才再出门；确实有人回家后又去了刚才满的那座站；同一趟出门不会走回刚满的站）；`node bots/evaluate.js v2 --write`：静态 ≥131 的 4 种、≥140 的 0 种。

### 2026-10-06 20:50 · v2.3：回家后先想 50 秒再开车 + 更陡的难度曲线（128 / 138 / 145 三档）

**规则**（`engine.js`）：v2.2 里满员或等太久、又换不了站的人，走回家就立刻开车，等于拿掉了玩家「救人」的窗口，也不像真人。改回：到家后和其他在家的人一样，最多考虑 50 秒（在总耐心之内），期间有合适的站还能再出门，否则开车。每人最多出门两次（就地换站也算一次）。

**难度**：发起人试玩觉得高分太容易——一站不挪就差点到 133。要求：不挪站时只有开局摆得非常准才过关，稍差就要靠挪站补救；高分必须有挪站；特别会挪站能拿到特别高的分。机器人（`bots/curve.js`）：

### 2026-10-06 20:35 · v2.2：规则更贴近现实（不越过港铁、满员就地换站）+ 重调高峰 + 新的开场过渡 + 「满」的新表达

**规则改了什么**（`engine.js`）——发起人试玩发现两处不现实：
- **有人走过港铁再坐车回来**（例：横洲东头围的人走 5 格、经过港铁站，去港铁南边的站，再坐车回港铁）。新规则：站要比港铁近才有人去——这些人今天开车，就是嫌走去港铁太远；要走得和去港铁一样远的站不会赢得他们。实现为 `shareAt()`：全程走路格数 ≥ 到港铁的格数时比例为 0。
